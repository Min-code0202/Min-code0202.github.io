우주오락실 · 고찰

실시간 게임 서버를 구현하며 Redis Pub/Sub 메시지 동기화와 STOMP 채널 backlog 튜닝에서 고민한 설계 판단을 정리했습니다.

Redis Pub/Sub 기반 메시지 동기화

멀티 인스턴스 환경에서 같은 방 유저의 실시간 메시지를 일관되게 전달하기 위해 정리한 설계 판단입니다.

1. Redis Pub/Sub을 처음부터 고려하지 못한 이유

초기에는 단일 인스턴스 기준으로 STOMP SimpleBroker를 사용했기 때문에 문제가 드러나지 않았습니다. 같은 서버 안에서는 /topic/room/{roomId} 구독 정보를 SimpleBroker가 메모리에서 관리하고 메시지를 정상 전달했습니다.

이후 부하 분산을 위해 백엔드를 멀티 인스턴스로 확장하면서, SimpleBroker의 구독 정보가 서버 메모리 내부에만 존재한다는 한계를 확인했습니다. 이를 계기로 서버 간 메시지 전파 계층이 필요하다고 판단했고, 이미 방 상태와 점수 저장소로 사용 중이던 Redis를 활용해 Pub/Sub 기반 동기화 구조로 개선했습니다.

2. PatternTopic은 클라이언트 브로드캐스트가 아니다

Redis의 PatternTopic("/topic/room/*")은 모든 클라이언트에게 메시지를 보내기 위한 장치가 아니라, 모든 백엔드 인스턴스가 방 메시지를 감지하기 위한 서버 간 패턴 구독입니다.

각 백엔드는 Redis에서 수신한 메시지의 roomId를 기준으로 다시 /topic/room/{roomId} STOMP destination에 재전달했습니다. 최종적으로는 해당 서버에 연결되어 있고, 해당 방을 구독한 클라이언트만 메시지를 받도록 처리했습니다. 개인 메시지는 대상 사용자의 연결 서버를 특정하기 어렵기 때문에 내부 채널로 모든 인스턴스에 전파한 뒤 실제 세션을 가진 서버에서만 전달하도록 했습니다.

3. 현재 구조의 한계와 개선 방향

Redis Pub/Sub은 구현 복잡도와 기존 인프라 재사용 측면에서 적합했지만, 모든 인스턴스가 모든 방 메시지를 수신하는 구조이므로 방과 메시지가 많아질수록 불필요한 fan-out 비용이 커질 수 있습니다. 또한 Pub/Sub은 메시지를 저장하지 않고, Kafka처럼 소비 속도 조절이나 offset 기반 재처리를 제공하지 않는 한계도 있습니다.

당시 프로젝트에서는 SimpleBroker의 서버 간 메시지 단절을 빠르게 해결하는 것이 우선이었고, 실시간 게임 메시지는 즉시성이 중요했기 때문에 Redis Pub/Sub이 합리적인 선택이었습니다. 다만 규모가 커진다면 각 인스턴스가 실제 유저를 가진 roomId 채널만 동적으로 구독하거나, RabbitMQ/ActiveMQ STOMP broker relay처럼 destination 라우팅을 외부 브로커에 위임하는 구조로 개선할 수 있다고 판단했습니다.

STOMP 채널 backlog 튜닝

100명 동접 테스트에서 접속 상태 불일치를 완화하며 정리한 성능 튜닝 기준입니다.

1. 스레드 풀 확장은 근본적인 튜닝이 아니다

100명 동접 테스트에서 DISCONNECT 처리가 분 단위로 지연되는 문제가 있었고, 이를 완화하기 위해 STOMP 채널 스레드 풀과 queueCapacity를 보수적으로 확장했습니다. 실제 테스트에서는 서버가 안정적으로 동작했지만, 2vCPU 환경에서 core 16 / max 64 / queue 20,000 설정이 최적값이라고 단정할 수는 없다고 판단했습니다.

2. 설정값 확대가 감출 수 있는 비용

스레드 수를 크게 늘리는 것은 컨텍스트 스위치 증가, 메모리 사용량 증가, 큐 적재로 인한 지연 은폐로 이어질 수 있습니다. 따라서 CPU 사용률, 메모리 사용량, active thread 수, queue depth, GC 지표, WebSocket 연결 수, DISCONNECT 처리 지연 시간을 Grafana, Micrometer, Actuator 같은 도구로 관찰하며 적정값을 찾아야 한다고 정리했습니다.

3. 이후 적용할 튜닝 기준

이번 경험을 통해 실시간 기능의 성능 개선은 설정값을 키우는 것이 아니라, 병목 지점을 관찰하고 지표를 기반으로 처리량과 안정성 사이의 균형을 찾는 과정이라는 점을 배웠습니다.

이후 유사한 실시간 시스템을 설계할 때는 부하 테스트와 모니터링 환경을 먼저 구성하고, 측정 결과를 기준으로 스레드 풀, 큐 크기, heartbeat 주기 등을 단계적으로 조정해야 한다고 판단했습니다.
