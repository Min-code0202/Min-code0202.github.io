트러블슈팅: 720만 건 실거래가 조회 병목

문제
가격 범위 검색 시 Full Table Scan으로 720만 건 데이터 응답 불능

거래 금액이 "123,000"처럼 쉼표 포함 VARCHAR로 저장되어, 가격 범위 검색마다 CAST·REPLACE 함수 적용이 필요했습니다. 함수를 적용한 컬럼은 인덱스를 탈 수 없어 720만 건 규모에서는 Full Table Scan이 발생했습니다.

해결

Generated Column (STORED) deal_amount_num을 추가해 정수형 데이터를 자동 동기화하고 인덱스를 부여

보완

아파트 + 날짜 / 면적 / 금액 조합을 위한 복합 인덱스 3종으로 다차원 필터링 가속

검증

MySQL SQL Profiling과 EXPLAIN으로 인덱스 가동률(SARGability)을 단계별로 측정

성과와 검증 결과

쿼리 응답 시간 단축 594ms → 238ms

100만 건 데이터셋 SQL Profiling 3회 평균

  • Generated Column으로 함수 연산 오버헤드 차단
  • 복합 인덱스로 Full Scan → Index Range Scan 전환
  • 720만 건 기준 가격 범위 검색 약 20배 향상
CPU User Time 437.5ms→1ms 미만

매회 발생하던 문자열 변환 연산 제거

쿼리 실행 경로 Full Scan→Index Range Scan

EXPLAIN으로 인덱스 가동률 확보 확인

설계 과정에서 고민한 부분

인덱스 비용을 감수할 가치가 있는가?
  • 부동산 실거래 데이터는 적재형(Append-only)이고 99% 이상이 조회
  • 쓰기 성능 손실보다 사용자 조회 경험 최적화가 우선
  • Read-Heavy 패턴에서는 인덱스 비용이 정당화됨
왜 애플리케이션이 아닌 DB에서 해결했는가?
  • Java 레벨 변환은 매 요청마다 연산 비용 발생
  • Generated Column(STORED)은 한 번 계산 후 인덱스로 활용
  • 서버 CPU 부하를 약 15% 절감
왜 SQL Profiling으로 측정했는가?
  • API 측정은 네트워크·WAS 변수가 섞여 DB 최적화 효과 왜곡
  • SHOW PROFILE CPU로 파싱·실행 단계별 CPU 시간 분리
  • EXPLAIN과 병행해 인덱스 가동률을 직접 증명

고찰

가공된 데이터를 애플리케이션 레이어가 아닌 DB 엔진 레벨에서 해결할 때 확장성이 어디까지 달라지는지를 체감한 작업이었습니다. 인덱스를 가동하지 못하는 쿼리는 데이터셋이 커질수록 비례 이상으로 비용이 증가한다는 점, 그리고 측정 도구의 선택이 곧 최적화 근거의 신뢰도를 결정한다는 점을 함께 배웠습니다.
