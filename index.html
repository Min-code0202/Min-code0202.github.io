트러블슈팅: 멀티 BE 클러스터 메시지 동기화

문제
로드밸런싱 환경에서 같은 방 유저가 다른 서버에 붙으면 게임이 둘로 분리

STOMP 기본 SimpleBroker는 in-memory라 백엔드 인스턴스 간 메시지를 공유하지 못합니다. 로드밸런싱으로 백엔드를 여러 대 띄우자 같은 방 유저가 서로 다른 서버에 연결돼, broadcast와 개인 메시지(랭킹·결과)가 서버 경계를 넘지 못하고 게임이 갈라졌습니다.

1차 시도

외부 STOMP 브로커(RabbitMQ relay)를 도입했으나, RabbitMQ STOMP는 destination에 /를 허용하지 않아(.만 routing-key separator) /topic/room/<UUID>가 "Invalid destination"으로 거부 → revert

해결

이미 게임 state에 쓰던 Redis Pub/Sub으로 전환 — BROADCAST는 PatternTopic("/topic/room/*")을 전 서버가 구독, PRIVATE는 envelope으로 fan-out해 세션이 있는 서버만 송신

검증

멀티 인스턴스 배포 환경에서 서로 다른 서버에 연결된 유저 간 broadcast·개인 메시지 정상 동기화 확인

트러블슈팅: 100명 동접 STOMP 채널 백프레셔

문제
100명 동시 접속에서 DISCONNECT 처리가 분 단위로 지연

STOMP 채널 스레드 풀이 기본값(CPU × 2)이라 2vCPU 서버에서는 4 스레드만 할당됐습니다. 100명 동접에 1.5초 주기 랭킹 broadcast가 겹치자 채널 큐에 backlog가 쌓이며 백프레셔가 발생했고, DISCONNECT 이벤트 처리가 분 단위로 밀렸습니다.

해결

STOMP 채널 스레드 풀을 core 16 / max 64 / queue 20,000으로 확장, queueCapacity를 명시해 무한 큐로 인한 OOM도 방어

보완

동접 카운터를 STOMP 이벤트 대신 Tomcat transport layer hook에서 갱신 → 채널 backlog와 무관하게 실시간 정확

보강

STOMP heartbeat를 10초로 설정 — OS TCP keepalive(2시간)에 의존하지 않고 dead session을 빠르게 감지해 ghost session 누적 차단

문제
AI 서버 지연 2초가 사용자 체감 30초 응답으로 증폭

AI 서버의 실제 지연은 약 2초였으나, 응답을 기다리는 동안 WAS 워커 스레드가 계속 점유되면서 후속 요청이 큐에서 대기하는 Thread Starvation이 발생했습니다. 이로 인해 사용자가 체감하는 응답 대기는 약 30초까지 누적되었습니다.

해결

202 Accepted로 요청을 먼저 접수하고 AI 호출은 @Async 작업으로 분리

보완

QUEUED / RUNNING / DONE / FAILED 상태로 작업 진행과 결과 조회 흐름 분리

검증

외부 네트워크 변수를 제거하기 위해 Mock AI 서버를 구축하고, k6 20VU로 동기/비동기 구조의 처리량과 완료 시간 비교

설계 과정에서 고민한 부분

왜 @Async를 선택했는가? (다른 비동기 방식 대비)
  • 직접 스레드·CompletableFuture 대비 풀 관리가 선언적, 추가 인프라 0
  • 기존 MVC·JPA 스택을 유지하며 무거운 작업만 오프로딩
  • 제한된 스레드 풀이 외부 AI 서버 동시 호출 수를 통제하는 보호막 역할
단순 @Async만으로 충분할까?
  • 백그라운드 처리만으로는 완료/실패 여부를 알기 어려움
  • 결과 조회 시점에 작업 진행 상태가 필요해 상태 저장 구조 추가
  • AnalysisJob과 결과 조회 API로 흐름 분리
왜 비디오만 비동기로 분리했는가?
  • 오디오 분석 결과는 꼬리질문 생성에 즉시 사용됨
  • 비동기로 분리하면 다음 질문 흐름이 끊김

트러블슈팅: 720만 건 실거래가 조회 병목

문제
WHERE/JOIN 컬럼에 함수가 적용되어 720만 건 데이터에서 Full Table Scan 발생

가격 검색에서는 거래 금액이 "123,000"처럼 쉼표 포함 VARCHAR로 저장되어 매번 CAST·REPLACE 함수가 적용되었습니다. 지역 JOIN에서는 법정동 코드 10자리에 LEFT(dong_code, 5) 함수가 적용되었습니다. 두 경우 모두 함수가 적용된 컬럼은 인덱스를 탈 수 없어, 720만 건 규모에서는 3-way JOIN과 함께 Full Table Scan이 발생했습니다.

해결

Generated Column (STORED)을 두 곳에 동일 패턴으로 적용 — 가격은 deal_amount_num, JOIN은 sgg_prefix로 함수 연산을 DB가 미리 계산해 인덱스 부여

보완

아파트 + 날짜 / 면적 / 금액 조합 복합 인덱스 3종으로 다차원 필터링 가속, JOIN용 (sgg_prefix, dong_name) 인덱스 추가

검증

SQL Profiling으로 CPU 시간을 측정하고, EXPLAIN으로 실행 계획 변화(type: ALL → range, key: NULL → idx_hd_apt_amount)를 확인해 인덱스 가동률(SARGability)을 직접 증명

성과와 검증 결과

쿼리 응답 시간 단축 594ms → 238ms

100만 건 데이터셋 SQL Profiling 3회 평균

  • Generated Column으로 함수 연산 오버헤드 차단
  • 복합 인덱스로 Full Scan → Index Range Scan 전환
  • 720만 건 기준 가격 범위 검색 약 20배 향상

설계 과정에서 고민한 부분

인덱스 비용을 감수할 가치가 있는가?
  • 부동산 실거래 데이터는 적재형(Append-only)이고 99% 이상이 조회
  • 쓰기 성능 손실보다 사용자 조회 경험 최적화가 우선
  • Read-Heavy 패턴에서는 인덱스 비용이 정당화됨
왜 Generated Column을 선택했는가? (4가지 대안 비교)
  • CAST/REPLACE 유지 — 함수 적용으로 인덱스 무력화, 데이터 증가 시 비용 폭증
  • 원본 컬럼 타입 변경 — 공공데이터 원본 보존 불가, 기존 적재 로직 마이그레이션 리스크
  • 별도 숫자 컬럼 + 애플리케이션 관리 — 두 컬럼 정합성을 앱 코드가 책임져야 함
  • Generated Column (STORED) — 원본 보존, 정합성은 DB가 보장, 인덱스 활용 가능
왜 SQL Profiling으로 측정했는가?
  • API 측정은 네트워크·WAS 변수가 섞여 DB 최적화 효과 왜곡
  • SHOW PROFILE CPU로 파싱·실행 단계별 CPU 시간 분리
  • EXPLAIN과 병행해 인덱스 가동률을 직접 증명
왜 apt_seq를 복합 인덱스 맨 앞에 두었는가?
  • 서비스 핵심 조회 패턴은 "특정 아파트의 거래 내역" 조회
  • apt_seq로 먼저 범위를 좁힌 뒤 날짜·면적·가격 조건 적용
  • 선택도가 가장 높은 컬럼을 선두에 두어 인덱스 가지치기 효율 극대화

고찰

가공된 데이터를 애플리케이션 레이어가 아닌 DB 엔진 레벨에서 해결할 때 확장성이 어디까지 달라지는지를 체감한 작업이었습니다. 인덱스를 가동하지 못하는 쿼리는 데이터셋이 커질수록 비례 이상으로 비용이 증가한다는 점, 그리고 측정 도구의 선택이 곧 최적화 근거의 신뢰도를 결정한다는 점을 함께 배웠습니다.
