우주오락실 · 메시지 동기화

멀티 인스턴스 배포 후 같은 방 유저의 실시간 메시지가 서버별로 분리되는 문제를 해결했습니다.

문제 상황
같은 방인데 EC2/C5a 중 어느 서버에 연결됐는지에 따라 게임 상태가 갈라짐

로드밸런싱 환경에서 A 사용자는 Backend A, B 사용자는 Backend B에 연결될 수 있었습니다. 이때 STOMP SimpleBroker가 인메모리로 동작해 한 서버에서 발행한 방 메시지가 다른 서버의 구독자에게 전달되지 않았습니다.

고민한 대안

처음에는 roomId consistent hash로 같은 방 사용자를 같은 BE에 고정했고, 이후 RabbitMQ STOMP relay도 검토했습니다. 하지만 hash 라우팅은 서버 장애/재접속에 약했고, RabbitMQ는 /topic/room/{uuid} destination을 거부해 운영 로그에 에러가 반복됐습니다.

판단과 해결

이미 Redis가 방 상태와 점수 저장소로 쓰이고 있었기 때문에 별도 브로커보다 Redis Pub/Sub이 더 단순했습니다. PatternTopic("/topic/room/*")로 방 브로드캐스트를 구독하고, /internal/private envelope로 개인 메시지를 모든 BE에 fan-out했습니다.

성과

RoomPublisher가 broadcast/private 전송을 Redis 기반으로 통합하면서 서버 위치와 무관하게 대기실, 게임 진행, 라이브 랭킹, 최종 결과 메시지가 동일하게 전달되도록 개선했습니다. 이후 실시간 기능은 공통 메시지 전파 기준을 먼저 설계해야 한다고 판단했습니다.

우주오락실 · 접속 상태 불일치

100명 동접 상황에서 STOMP 채널 backlog와 비정상 이탈 처리로 방 인원이 어긋나는 문제를 해결했습니다.

문제 상황
100명 동접에서 DISCONNECT 처리가 밀리며 사용자가 방에 남아있는 것처럼 보임

브라우저 창 닫기·뒤로가기처럼 명시적 ROOM_LEAVE가 전송되지 않는 이탈에 더해, 1.5초 주기 랭킹 broadcast가 겹치면서 STOMP 채널 큐에 backlog가 쌓였습니다.

원인 확인

2vCPU 서버에서 STOMP 채널 기본 스레드 풀은 CPU x 2 기준 4개였습니다. 동접 메시지와 이탈 이벤트가 같은 채널에서 처리되면서 DISCONNECT 반영이 분 단위로 지연됐고 ghost session처럼 보였습니다.

판단과 해결

채널 스레드 풀을 core 16 / max 64 / queue 20,000으로 확장하고, FE cleanup과 SessionDisconnectEvent를 함께 사용했습니다. 재연결 오판을 줄이기 위해 10초 grace period와 heartbeat 10초도 적용했습니다.

성과

정상 이탈, 새로고침, 멀티탭, 비정상 종료를 구분하고 transport layer connect/close로 실제 연결 수를 분리했습니다. 방 인원 표시와 실제 WebSocket 연결 상태를 안정적으로 맞췄습니다.

우주오락실 · CNN 브라우저 이식

직접 학습한 Quick Draw 이미지 분류 모델을 실제 게임 로딩 흐름 안에서 사용할 수 있도록 개선했습니다.

문제 상황
모델은 학습됐지만, 브라우저 게임에서는 로딩 실패와 첫 라운드 지연이 발생

Quick Draw 49클래스 CNN 모델을 Keras 3.13에서 TF.js 4.22 형식으로 변환했지만, InputLayer.batch_shape와 sequential_N/ weight prefix가 TF.js loader와 맞지 않았습니다. 또한 모델 자산이 약 5.3MB라 첫 진입 시 “AI 모델 로딩 중” 화면이 자주 보였습니다.

판단과 해결

모델을 다시 학습하기보다 변환 결과를 메모리에서 보정하는 방식이 더 적합하다고 판단했습니다. batch_shape를 batch_input_shape로 바꾸고 weight prefix를 제거한 뒤 shard를 병합해 tf.io.fromMemory로 로드했습니다.

입력 정합성

브라우저 캔버스 입력은 학습 데이터와 달라질 수 있어 stroke bounding box, 1.2배 padding, 28x28 resize, 흑백 반전/정규화로 모델 입력 [1,28,28,1]과 맞췄습니다.

성과

GAME_LOAD 시점에 model.json과 bin shard를 prefetch하고 7초 튜토리얼 카드를 추가해 사용자가 로딩 지연을 체감하지 않도록 했습니다. 이후 Top-K 예측 결과를 라운드 점수 판정에 연결했습니다.

DADAP · 분석 요청 병목

문제 상황
AI 서버 지연보다 WAS 요청 스레드 점유가 병목

AI 서버 지연은 약 2초였지만, 응답을 기다리는 동안 Spring 요청 스레드가 점유됐습니다. 동시 요청이 늘어나며 후속 요청이 큐에 쌓였고, 체감 대기는 약 30초까지 증가했습니다.

해결

상태 관리

AnalysisJob에 QUEUED, RUNNING, DONE, FAILED 상태와 결과를 저장하고, 별도 조회 API로 완료 여부를 확인하도록 분리했습니다.

검증과 성과

Mock AI 서버와 k6 20VU로 비교했습니다. 요청 접수 응답은 30,654ms → 102ms, 처리 완료 요청 수는 80건 → 580건, 전체 완료 시간은 40,737ms → 25,347ms로 개선됐습니다.

설계 판단

오디오는 꼬리질문 생성에 즉시 필요해 동기로 유지했습니다. 비디오는 사후 피드백 성격이라 비동기로 분리하고, 제한된 스레드 풀이 AI 호출 수를 제어하도록 했습니다.

조회 조건의 문자열 가공으로 인한 인덱스 미사용 문제 해결

문제
WHERE/JOIN 조건에서 컬럼에 함수가 적용되어 대량 스캔이 발생하는 구조

약 726만 건의 거래 데이터를 지역, 단지, 가격, 면적 조건으로 조회했습니다. 서울 조건 조회 시 약 454만 건이 조회 후보가 되었고, 운영 지도 조회 쿼리는 최대 67초까지 지연됐습니다. 병목은 단순한 인덱스 부재가 아니라 WHERE와 JOIN 조건에서 컬럼 값을 매번 가공해 인덱스를 활용하기 어려운 구조였습니다.

726만 건 운영 테이블에서 지역 조인·정렬 포함 지도 조회 검증

Before

조회 시마다 CAST(REPLACE(...))가 수행되어 문자열 가공 비용이 발생했습니다.

WHERE CAST(REPLACE(deal_amount, ',', '') AS UNSIGNED) BETWEEN ? AND ?
After

조회 시 문자열 변환 없이 미리 계산된 숫자 컬럼을 비교하도록 변경했습니다.

WHERE deal_amount_num BETWEEN ? AND ?
인덱스

사용자는 특정 단지를 선택한 뒤 가격·면적·기간 필터를 적용하는 경우가 많았습니다. apt_seq로 후보 거래를 먼저 줄이는 조회 패턴에 맞춰 복합 인덱스를 구성했습니다.

(apt_seq, deal_amount_num) (apt_seq, deal_year, deal_month, deal_day) (apt_seq, exclu_use_ar)
검증

100만 건 비교 테이블에서는 가격 조건만 분리해 SQL Profiling으로 측정했습니다. 726만 건 운영 테이블에서는 EXPLAIN ANALYZE로 지역 조인·정렬 포함 쿼리를 검증했습니다.

ZipCheck · 해결 과정과 판단

단순 인덱스 추가가 아니라, 쿼리 조건이 인덱스를 사용할 수 있는 형태인지부터 다시 설계했습니다.

선택 근거와 트레이드오프

마이그레이션 절차
  1. 먼저 원본 데이터 건수와 deal_amount 형식이 숫자·쉼표 조합인지 점검
  2. 임시 숫자 컬럼에 변환 가능한 데이터만 이관해 변환 실패 케이스를 분리
  3. 검증 후 deal_amount_num STORED Generated Column으로 전환
  4. 데이터 정합성 확인이 끝난 뒤 복합 인덱스를 마지막에 적용
왜 Generated Column을 선택했나?
  • 기존 방식 유지는 조회마다 문자열 파싱 비용이 반복되어 근본 해결이 아니었습니다.
  • 원본 금액 컬럼을 숫자로 바꾸면 공공데이터 원본 보존과 기존 적재 로직에 영향이 컸습니다.
  • 앱에서 숫자 컬럼을 직접 관리하면 원본 값과 변환 값의 정합성을 코드가 책임져야 했습니다.
  • Generated Column은 원본을 보존하면서 변환 값의 정합성을 DB가 관리하고, 인덱스도 적용할 수 있었습니다.
왜 apt_seq를 인덱스 선두에 뒀나?
  • 서비스의 핵심 흐름은 사용자가 지역이나 단지를 선택한 뒤 거래 내역을 좁혀 보는 방식이었습니다.
  • apt_seq로 후보 거래를 먼저 줄이고, 그 안에서 날짜·면적·가격 조건을 적용하는 편이 효율적이었습니다.
  • 전국 전체 가격 검색보다 단지 기준 상세 조회의 체감 성능을 우선했습니다.
트레이드오프

STORED Generated Column과 복합 인덱스는 저장 공간과 데이터 적재 시 인덱스 갱신 비용을 늘립니다. 다만 실거래가 데이터는 한 번 적재되면 수정·삭제가 거의 없는 read-heavy 데이터라, 쓰기 비용보다 조회 응답성을 우선했습니다.
