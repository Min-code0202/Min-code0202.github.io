트러블슈팅: AI 분석 요청 병목

문제
동시 접속 테스트에서 다음 질문 전환이 30초 이상 지연

AI 서버 응답을 기다리는 동안 백엔드 요청 스레드가 점유되는 동기 처리 구조가 원인이었습니다.

해결

202 Accepted로 요청을 먼저 접수하고 AI 호출은 @Async 작업으로 분리

보완

QUEUED / RUNNING / DONE / FAILED 상태로 작업 진행과 결과 조회 흐름 분리

검증

k6 20VU 테스트로 동기/비동기 구조의 처리량과 완료 시간 비교

검증 결과

전체 분석 완료 시간 40,737ms→25,347ms

전체 영상 분석 흐름 시간 단축

즉시 응답 구조 30,654ms→102ms

AI 작업 완료 대기 없이 요청 접수

설계 과정에서 고민한 부분

단순 @Async만으로 충분할까?
  • 백그라운드 처리만으로는 완료/실패 여부를 알기 어려움
  • 결과 재조회가 필요해 상태 저장 구조 추가
  • AnalysisJob과 결과 조회 API로 흐름 분리
왜 k6로 검증했는가?
  • 체감 지연만으로는 구조 변경 근거가 부족함
  • 동시 요청 상황을 재현해 병목 원인 확인
  • 처리량과 전체 완료 시간을 수치로 비교

고찰

외부 AI API처럼 응답 시간이 긴 작업은 요청 접수와 작업 완료를 분리해야 사용자 응답성과 서버 안정성을 함께 확보할 수 있었습니다. 다만 분석 실패 사유와 재시도 이력, 부하 테스트 결과를 더 체계적으로 남기지 못한 점은 아쉬움으로 남았습니다.

  • 상태 기반 비동기 처리는 결과 조회와 실패 추적까지 함께 설계되어야 했습니다.
  • 부하 테스트 자동화와 결과 기록 체계를 보완하면 같은 조건의 재검증이 더 쉬웠을 것입니다.
